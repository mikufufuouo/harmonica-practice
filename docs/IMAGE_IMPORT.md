# 公众号 BD + 歌词图片导入路线

本文维护路线与数据契约；交付进度及下一包以 [STATE.md](STATE.md) 为准。

2026-09-14 用户说明：当前主要谱源为公众号的 BD 与对应歌词图片。图片应成为主要入口；手工/粘贴文本作为基础能力与识别失败后的修正入口。最终路径是图片 → 识别草稿 → 人工确认 → 本地谱库 → 跟练。

## 产品决定

优先验证「本地 OCR + 排版分区 + BD 规则诊断 + 人工确认」。不直接把通用视觉模型输出写入谱库。主要原因是用户偏好 local-first，而识别结果的校对成本与漏音风险比“看起来识别出一整页”更重要。

第一版允许用户裁剪谱区、选择 BD 行和歌词行，降低复杂排版的自动定位风险。识别数字/B/D 与识别中文歌词分别处理，保留横向坐标及行框。标题、二维码、水印和广告不是歌曲音符。清晰短截图优先，长图自动切块须处理重叠去重，防止重复导入或漏掉跨块行。

OCR 原文、候选与用户修正三者分开保存。`B ↔ 8`、`D ↔ 0/O`、`1 ↔ I/l` 等只提出候选，不按合法 BD 语法自动替换成确定答案。某个识别结果即便语法合法（如把 4B 看成 4D），也可能错误；语法检查不能当正确性检查。

音符序列最终仍是与乐器无关的 NoteSequence，BD 是图片里的来源表述和针对选定琴的派生指法。原谱琴调未知时可保存待处理草稿，但不能保存为已确认的实际音高歌曲。图片上的歌曲调与原谱口琴调不能混为一个字段。

## 用户流程

1. 从相册选图，裁剪需要的谱区，填写/确认原谱口琴调。所有步骤默认本地。
2. 对每行显示「原图小区域 + 识别的 BD + 歌词行」；点错字直接编辑。可手动切分/合并行，补漏音、删重音，调整行顺序。
3. 重点标出低可信字符、未覆盖区域、无效孔号、无法解释的音乐符号、疑似重复/漏行。数字/方向等不同置信度分别保留，模型分数不冒充校准概率。
4. 用户确认每个乐句/区域，歌词先确认到行。一个字可能配多个音，多个字也可能落在一个长音范围，不能按字数自动一一绑定。
5. 结构检查无阻塞错误、必需区域已人工确认、原谱琴调明确后，生成版本化 NoteSequence 并存本地曲库。保留审核记录与来源回看。未确认草稿不能开始评分跟练。

延音线、休止、重复、括号和弦等若当前不支持，必须提示；不能因为识别了大部分 `4B` 就宣称整曲已经导入。图片没有提供明确节奏时，保存未知时间，未来只启用逐音模式。

## 数据层：三个对象，而非混在一张表

- `SourceAsset`（未来实现）：本地 IndexedDB Blob、assetId、mime、尺寸、内容哈希、可选用户提供来源名称；不把图片 base64 塞进歌曲 JSON。保留原图坐标到裁剪/缩放/旋转图的变换，便于点击音符回原图。
- `ImportDraft`（未来实现）：sourceAssets、orderedRegions（BD/lyrics/heading/unknown）、每 token 的原始字符串/候选/区域/置信证据、原谱琴配置、blocker diagnostics、人工修改记录、`draft/needs-review/confirmed` 状态和revision。编辑已确认的区域使对应确认失效，防止陈旧确认直接入库。
- `LibraryEntry`（未来实现）：entryId、sequenceId、sequenceRevision、已确认 NoteSequence、sourceAssetRefs、审核摘要、创建/更新时间。Song 不依赖图片存在才能播放；备份可选择歌曲 JSON 或含原图包。备份保留歌词与引用，删除来源图后明确显示来源不可回看。

本轮已预留 SourceRef 的图片 region、source.format=image 与独立 lyrics 行。未实现自动歌词对齐、OCR 模型、草稿状态机或谱库，这些要成套交付。

## Roadmap：与音频验证并行，排在完整跟练之前

| 包 | 实际交付 | 进入下一包的依据 |
|---|---|---|
| S0，本轮 | NoteSequence、BD 文本适配、歌词未对齐行、指法预览；来源坐标契约 | 同音/换琴/移调/错误符号/歌词保存的测试通过 |
| S1，下个谱面包 | 本地谱库 + 图片原图旁的人工录入/校对草稿，逐行确认后保存 | 在手机完成一首短谱，刷新后歌曲与草稿可恢复，JSON 备份往返无丢音/歌词 |
| S2，图片识别试验 | 给 S1 加本地 OCR、BD/歌词分区及候选纠错 | 用真实公众号截图测音符准确率、行序/歌词匹配和人工修正耗时；没达到收益就保留手工录入 |
| S3，接入跟练 | 已确认短谱用于逐音跟练；节奏未知则不做节奏评分 | 对照确认后的谱逐事件核对；音频反馈必须另外通过音频路线门槛 |
| S4，复杂输入扩展 | 更复杂长图、更多方言、必要时可选视觉模型；MIDI/XML适配按实际需求进入 | 由真实失败样本决定，不一次铺完所有来源 |

S1 的手动校对界面先做好，后续 OCR 或视觉模型都输出同一种草稿，算法切换不会重写谱库/跟练系统。图片识别不必等串孔算法成熟；跟练评分必须等待音频路线自己的证据。

## 第一轮技术实验

样本先收集用户常见版式的 10–20 张截图（分辨率/压缩/浅色背景/水印/长图），只本地使用。划分开发/留出时按文章或版式组，不能把同图不同裁剪分到两边。缺少实际样例前不宣称任何 OCR 准确率。

基线 A：裁剪后的 BD 行用轻量字符 OCR，中文歌词另行识别，空间信息只建议行配对。可先试 Tesseract.js（WASM + Worker），按需下载/缓存语言数据，应用初始包不捆绑整个 OCR 模型。[项目说明](https://github.com/naptha/tesseract.js/) 明确支持浏览器执行；其识别精度和移动端速度仍须我们实测。

基线 B：如果 A 对常见细字体/复杂背景效果差，评估可在 ONNX Runtime Web 跑的检测+识别模型，必须核对模型许可证、体积、内存与实际设备支持；WASM作为基础，不能假设用户设备都支持 WebGPU。[ONNX Runtime Web](https://onnxruntime.ai/docs/tutorials/web/)。

可选 C：视觉模型只处理复杂版面或用户主动要求的难图。默认不上传；若采用云端，界面需清楚让用户选择发送的裁剪图及服务，密钥不能写进公开 PWA。视觉模型也输出候选/区域并经过人工校对，不可以“纠错”名义补造音符。此路线暂不实现。

先纠偏、分区再识别，而不是无条件高分辨率放大；倾斜会影响行分割，局部识别也应选择相应分割模式。[Tesseract 图像质量建议](https://tesseract-ocr.github.io/tessdoc/ImproveQuality.html)。

主要衡量：BD token 完全匹配率（孔与B/D都对）、漏/增音数、行顺序正确率、歌词行字符错误率及配对准确率。产品门槛起点：留出清晰截图 BD token ≥95%，但不据此自动确认；同一首谱人工修正总时间相对纯手输至少减少一半，并且最终确认对照中无漏/重音。另测主要手机的冷启动下载量、p95耗时、内存/崩溃和离线复用。数字是目标，不是现有结果。

## 样例与公开测试边界

少量代表性图片用于确定真实语法/排版及设备体验；没有真实图时可用自造图开发 S1，但不能宣称通过真实版式验收。整首版权谱图/歌词不放进公开 GitHub 的测试资源，公开测试仅使用自造短样本。用户自己的本地谱库不随 Pages 部署发布。
